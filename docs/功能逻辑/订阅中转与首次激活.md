## 1. 双订阅入口

用户首页为面板返回的每种订阅地址展示一组选择：

| 入口 | 数据流 | 适用情况 |
| --- | --- | --- |
| 主用 · 本站中转 | 客户端 → 用户端服务器 → 原站订阅服务 | 用户直连原站不稳定，但用户端服务器能够访问原站 |
| 备用 · 原站直连 | 客户端 → 原站订阅服务 | 用户自行复制原站地址导入 |

这是订阅内容中转，不是代理节点流量中转，不改节点服务器地址。客户端自行选择和导入，不声称能够自动切换。服务器不会向客户端发送 302 跳转来冒充中转，也不使用第三方订阅转换器。

主用地址使用部署配置 `PORTAL_ORIGIN`，形如 `https://本站地址/sub/签名凭证`，不含管理登录后缀。本站地址可以是当前服务器公网 IP，也可以是指向它的域名；IP 必须有匹配且被客户端信任的 HTTPS 证书。不能自动把监听用的 127.0.0.1 当作公网地址，也不能依赖浏览器 Host 拼接公开链接。

安装页或站点设置中的“原站订阅来源”每行填写协议、主机、端口，例如 `https://sub.example.com:8443`，不填写路径。最多 8 项，留空只允许面板同源。订阅服务与面板不同端口/域名时必须加入对应来源；缺少配置时主用按钮不可用，原站备用仍显示。

门户服务器需同时能访问面板 API 和原站订阅。原站服务彻底停机、门户到原站也被阻断、API 凭据失效时，中转同样不可用。当前不缓存离线订阅副本，不承诺恢复原站故障或必然提速。

## 2. 中转权限与失败规则

`GET /sub/凭证` 使用专用 HMAC 签名，不需要浏览器登录 Cookie，适用于订阅客户端。签名包含门户用户 ID、原始地址摘要以及客户端 ID/subId 的状态摘要；密钥由现有主密钥按独立用途派生。目标 URL 不从请求参数读取，链接内不直接编码原站订阅秘密。

流程：签名验证 → 限速及并发限制 → 本地账号已激活且未停用 → 面板绑定 ID 核对 → 状态及独占订阅校验 → 在面板当前链接列表中匹配地址摘要 → 来源白名单 → 服务端取回内容 → 再次检查本地停用状态 → 返回订阅。

客户端原始 User-Agent/Accept 在限长后保留，用于原站选择订阅格式。管理 Token、Cookie、来源 IP 和任意请求头不转发给订阅服务。HTTPS 验证保持开启，不使用环境代理，不跟随重定向。远程明文 HTTP 订阅暂不支持中转，可使用原站备用；回环地址允许 HTTP。

每次最多读取 8 MiB，整条链路 45 秒超时，取订阅 HTTP 请求最多 20 秒；进程内最多 8 个并发、每用户每分钟 12 次、全局每分钟 300 次。返回受限的文本/YAML/JSON/二进制订阅类型；HTML 错误页拒绝。仅转发 Subscription-Userinfo、Profile-Update-Interval、Profile-Title，响应 no-store，不透传原站 Cookie 或 Location。

签名篡改、目标不再属于该用户、共享 subId 或未激活/停用账号拒绝中转；过期、流量耗尽或面板停用返回不可用。网络和上游错误明确失败，不输出错误网页假装订阅，也不跨用户复用缓存。

原站 subId 重置后，旧中转地址的后续请求会因状态摘要不匹配失效，用户重新复制主用和备用。账号停用也禁止中转；重新启用后仍匹配当前 subId 的旧中转链接会恢复可用，停用不是永久撤销凭证。修改本站登录密码不撤销订阅链接。跨系统在途请求仍有状态漂移窗口，不能保证已经发送的数据被收回。

## 3. 邀请码注册与首次密码

1. 站长在“邀请用户”选择已存在的面板客户端并生成专属邀请码，不再填写独立登录账号。后端默认以客户端 email 标识作为登录名称；现有账号继续使用原名称。
2. 后端核实客户端归属，在同一事务中创建无密码的待激活账号和随机邀请，返回 24 小时有效的一次性邀请码及等价快捷邀请链接。邀请码为 32 随机字节的 43 位 Base64URL 字符串，数据库只保存 SHA-256 摘要。待激活记录用于预留唯一绑定，用户无须额外创建或添加账户。
3. 站长通过可信渠道将邀请码交给对应用户。用户在登录页选择“邀请码注册”，粘贴并提交；也可以使用快捷链接，链接使用 `#activate=凭证`，页面读取后从地址栏移除；打开页面不自动消费，用户点击“验证邀请码并继续”才提交。
4. 验证通过后，原子消费邀请并签发 10 分钟有限会话。用户可以不输入旧密码进入，但只能读取自身基本身份、退出或设置首次密码；前后端都禁止查看订阅、流量和执行管理操作。
5. 用户设置并确认本站密码，后端 bcrypt 哈希保存，仅写门户数据库。提交时再次核实会话尚有效且账号仍未设密码，防止邀请重发后的旧请求抢占。
6. 成功后在同一事务内删除邀请及所有旧会话，签发新的 12 小时正常会话并轮换 CSRF，页面直接进入首页。之后使用账号和新密码登录，不再允许该账号免密码激活。保存成功但刷新身份失败时可重试进入首页，不重复提交密码。

邀请码兑换额外限制为每 IP 每 15 分钟 20 次、全局每分钟 60 次；登录保留独立的 IP、账号及全局限流。无效、过期、已使用或停用账号的邀请统一拒绝。限流为进程内固定窗口，重启清空，多实例不共享。

不能仅凭面板 email、用户名、subId 或原站订阅地址认领账号，因为它们不能可靠证明账号归属。管理员自身仍在安装时设置密码，不进入免密码流程。

链接过期、被消费但未完成设置、会话过期或激活响应丢失时：先刷新检查是否仍有有限会话；否则联系站长“重发邀请”。重发立即废弃旧链接和旧有限会话，只对未设密码且启用的账号开放。已激活账号不能靠重发邀请覆盖密码。停用账号会撤销邀请与会话。

## 4. 数据结构、接口与升级

- 本次邀请码流程继续使用版本 2，无新表、无迁移。历史模式版本从 1 升为 2：新增 `activations(user_id,token_hash,expires_at)` 和 `site.relay_origins`。`password_hash=''` 只表示待激活，不是可用于登录的空密码。
- 新接口：登录入口下 `POST api/activate`、`POST api/first-password`；管理员 `POST api/admin/invite`。`POST api/admin/invitations` 接收 email/clientId，返回 invitationCode、activationUrl、expiresAt、username；无须 username 或 password。原 `POST api/admin/users` 保留兼容，但界面只提供邀请流程；`POST api/admin/invite` 用于重发。
- `api/me`/用户列表增加 `mustSetPassword`；摘要增加 `routes`（primary、backup、reason）；设置增加 `relayOrigins`。
- 既有用户密码、管理员、绑定及会话保持现有数据；不会把已经有密码的用户降级。已有版本 1 数据库必须手动执行 [迁移 SQL](../sql/002_activation_relay.sql)，详见 [SQL 说明](../sql/README.md)。启动和 init 都不会替已有数据库自动升级。
