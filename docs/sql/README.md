# 数据库初始化与变更

本项目独立使用 SQLite，不连接 3x-ui 数据库。

初始结构的唯一可执行 SQL 为 [schema.sql](../../internal/store/schema.sql)，由 `portal init` 显式执行；服务启动 `serve` 不执行建表或自动迁移。本轮没有执行该 SQL。

- 适用范围：门户全新 SQLite 数据库，模式版本 2。
- 前置条件：确认独立数据目录、独立主密钥路径，目录可写，目标不是面板数据库。
- 顺序：生成并保护主密钥 → 执行初始化 SQL → 生成一次性安装凭证 → 启动服务 → 浏览器确认安装。
- 重复执行：建表使用 IF NOT EXISTS，但这不是升级迁移；已安装站点的 init 命令拒绝重置，不覆盖管理员和登录路径。
- 回滚：全新空安装可在停止服务并确认无业务数据后由操作者移除这套新数据与密钥；已有业务数据时必须从同一组备份恢复。不要删除主密钥尝试找回密码。
- 实际执行情况：本轮在自动测试中初始化隔离 SQLite；未操作真实 3x-ui 数据库。生产安装与 SQL 执行待操作者在目标环境手动完成。

## 已有版本 1 → 2

[002_activation_relay.sql](002_activation_relay.sql) 新增邀请表和订阅来源配置列，保留已有账号密码、绑定与管理员。新程序要求版本 2，不自动迁移；全新数据库不执行此迁移。

在已授权的目标服务器停止门户并备份整个数据目录与主密钥，确认目标库 `schema_version` 为 1 后，由操作者执行：

```bash
sudo -u portal-svc sqlite3 -bail /var/lib/3x-ui-portal/portal.db < docs/sql/002_activation_relay.sql
```

需预装 sqlite3 命令行工具。`-bail` 保证错误后停止并随连接退出回滚未提交事务，不能忽略错误继续提交。脚本仅执行一次：含版本检查及非幂等 ALTER TABLE，重复执行应失败。执行后核实版本为 2，再启动新版程序。

回滚：停服，恢复迁移前完整数据库目录并使用对应旧程序；主密钥保持匹配，不删除密钥。不要在已有新邀请/业务写入后直接删列冒充无损回滚。

本轮只交付 SQL，未运行本地或生产迁移，SQL 运行验收待完成。
